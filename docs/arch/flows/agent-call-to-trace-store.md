# From an agent call to the trace store (FL-TRACE)

This flow follows one question from the moment a service receives it to the moment its spans are handed to the trace store. The library supplies the calls; a consumer decides where to place them, which ids to carry between services, and which fields to map. So the flow can only be read through a consumer. The consumer read here is `edgy-solutions/invincible-agent`, on its conversation path: a question arrives at its backend-for-frontend (the BFF), a run of its orchestrator plans and executes the work, an analyst agent with model calls and tools answers it, and engines read their stores for the agent.

Its reference elements are the five component records: [trace entry](../components/trace-entry.md) (CO-ENTRY), [span carriers](../components/span-carriers.md) (CO-SPANS), [replay-safe boundary](../components/replay-safe-boundary.md) (CO-BOUNDARY), [emission witness](../components/emission-witness.md) (CO-WITNESS) and [mapping and redaction](../components/mapping-and-redaction.md) (CO-MAPPING).

**This record describes; it proposes nothing.** Statuses are those of [the README](../README.md). Library line numbers are at the leaf pin listed there (`e84fd29`); consumer line numbers are at `6b3e8ef`. Nothing here was measured: no trace was read back from a store. The record shape is provisional.

## Findings

1. **What is emitted is OpenTelemetry spans with Langfuse trace attributes, and nothing else.** Entries, boundary spans, step spans and decorated functions are spans; each model call is a generation observation. The library and this consumer emit no logs or metrics to the store. The model-call generation is written by the consumer's own wrapper through the SDK, not by a library carrier. `built`
2. **Where it lands is the SDK's exporter: a batch processor, then OTLP over HTTP to `/api/public/otel/v1/traces` on the configured host.** The host is the SDK's setting, and it defaults to the vendor's cloud service ([emission witness](../components/emission-witness.md), findings 2 and 3). The consumer's host is deployment configuration, which this record does not read. Each orchestrator step runs in its own process and flushes at its end, because the process would exit before the batch timer fires. `built`
3. **One trace id travels the whole path.** The BFF takes the id from a W3C `traceparent` header, else from `X-Trace-Id`, else mints 32 hex characters. It passes the id to the orchestrator run's configuration and, as `X-Trace-Id`, to every service it calls. Every receiver seeds its entry with it. A 32-hex id is used unchanged at every hop, so all hops share one trace id ([trace entry](../components/trace-entry.md), finding 3). One receiver, the analyst's `/analyze` proxy, mints a dashed id when the header is missing; that id is hashed, which is consistent on every later hop. `built`
4. **The trace holds together; its tree does not.** The parent span id travels with the trace id from the BFF to the orchestrator steps, from the steps to engines they call directly, and to engine-o and engine-docs. It is dropped at four places: the middlewares of engine-w and engine-f do not read it; the analyst's `/analyze` proxy reads the trace id and not the parent, so the analyst's boundary span is a root; and the analyst's tools send `X-Trace-Id` and no parent, so every engine entry a tool reaches is a root as well. Each such root sits on the right trace. Its link to the span that caused it is lost, so a reader of the store sees several roots in one trace. `built`
5. **The person is carried by two entries and not by the rest.** The mapping fills the trace's user from the consumer's `authz_id`. The BFF's entry passes it, and so does the analyst's boundary; every span opened inside either inherits it ([trace entry](../components/trace-entry.md), finding 6). The orchestrator's step spans pass the session and no person. The four engine entries pass no person; engine-docs passes the session. Because the analyst's tool calls start roots in other processes (finding 4), nothing reaches those engine entries by inheritance either. A store query by user finds the BFF's and the analyst's spans, not the engines' or the steps'. `built`
6. **The store read has no span of its own.** An engine's graph, vector or ontology query runs inside the engine's entry span, which covers the whole request. The one retrieval-typed span on the path is the analyst's memory lookup, and it records sizes only. So the trace shows which engine was called and for how long, not which store query ran or how long that took. `built`
7. **No content reaches the trace by the consumer's own code.** The consumer turns the SDK's input and output capture off before the SDK is imported, and its decorator wrapper forces both flags off ([span carriers](../components/span-carriers.md), finding 4). Its model-call wrapper records the model id, token counts and error level, and no prompt or completion. Its observation update writes sizes, not text. The mapping redacts nothing, because it projects none of the fields it lists as content-bearing ([mapping and redaction](../components/mapping-and-redaction.md), "Not established from code"). One path is outside this: see the first item of "Not established from code". `built`
8. **The model call is tied to the trace two ways.** The generation nests under the current span, which is inside the analyst's boundary. The consumer also stamps the model's LiteLLM metadata with the same trace id, the person and the session, through the library's `litellm_metadata` ([span carriers](../components/span-carriers.md), finding 3). `built`
9. **A lost span is counted in the process that lost it, and nowhere else.** Each process installs the export witness on its first entry; a refused batch adds its span count to that process's counter, and so do the consumer's own soft failures ([emission witness](../components/emission-witness.md), findings 5 and 10). Whether the consumer publishes the counter is not established. `built`

## Gaps

- **The parent is dropped at four receivers** (finding 4; steps 6, 10 and 11). The library offers the parent on every entry; the consumer does not forward or read it there. `built`
- **Most of the path carries no person** (finding 5; steps 4 and 11). `built`
- **The store read is invisible** (finding 6; step 12). `not built`
- **Nothing shows that spans arrived** (step 15; [emission witness](../components/emission-witness.md), finding 8). The library ships no read-back check, and the consumer read here has none on this path. `not built`

## Not established from code

- **Whether LiteLLM sends content of its own.** The consumer's telemetry module, on import, names Langfuse as LiteLLM's success and failure callback through two environment variables. The analyst's model is a LiteLLM model, an OpenAI-compatible client or a Hugging Face client, depending on settings. Whether LiteLLM reads those variable names, and what its Langfuse callback would send, is LiteLLM's behaviour; this record did not read it. That path would not pass through the library or its capture settings.
- **How long a span waits before export.** The batch processor's queue size, batch size and delay are the SDK's and OpenTelemetry's defaults or settings; this record did not read them.
- **Whether the store shows the roots of finding 4 as one trace.** The docstring of the replay-safe boundary says children whose parent was never exported appear as roots on the right trace. No test reads a trace back from a store.
- **Whether the consumer publishes the miss counter** (finding 9).
- **The consumer's export host and environment.** These are deployment settings.
